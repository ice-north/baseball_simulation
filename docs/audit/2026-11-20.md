## 最適化

1. **書き込みのたびの索引作りが約9倍速く**（`c487c495`）。全球団・全選手の情報の索引（`buildArchiveIndex`）が、選手ごとに今季の比較値（288人ぶん）を、球団ごとに成績の文脈を作り直していた → 1つを使い回す。出力は前と同じ（sha256 一致）。1年目8月 3.7秒 → 0.39秒、2年目6月 4.0秒 → 0.44秒。定期進行・編成の保存など、ほぼ全部の書き込みで効く。
2. **保存の芯（毎回読み書き）を 7.8MB → 1.5MB に**（`fe36ff67`）。
   - 年齢による能力の変化の一覧（`season.ageReports`。世界の全選手 約1.6万人ぶん）は一人用のキャンプ画面だけが読み、オンラインは `offseasonChanges` で別に作っている → 年度更新と毎日の進行で消す（2年目の芯のうち 6.2MB）。
   - 保存する試合結果の試合中の記録（`decisionLog`・`pitcherAppearances`。1試合約1KB×2か所）は、勝敗投手を試合の直後に `decisions` へ確定したあと誰も読まない → 外す。
   - どちらも中身を軽くするだけなので版は上げない（古いコードが読んでも困らない）。保存の合計（gzip）は 8103KB → 7570KB、読み書きの JSON の文字列化・解析もその分減る。
   - `size-budget.json` の core・records・storedGzip・otherParts を締め直した（いまの大きさ×1.2）。
3. 保存の部分（`publishPart`）と索引（選手・球団・年ごとの試合）の上げ直しを、1つずつ待たずに並べて待つ（往復の数だけ縮む）。

## 判断がほしいもの

1. **書き込みの最初（`online_claim`）が、参加者全員ぶんのビュー（1人約300KB）を毎回 Supabase から受け取っている**（`returning *`）。使うのは数列だけ。PostgREST の列の絞り込み（`?select=generation,snapshot_path,…`）で減らせるが、本番の PostgREST で確かめる必要があるので今回は入れていない。
2. **`season.results` と `schedule[].result` の二重持ち**（1年目8月の芯で約1.8MB。今回の削減後も残る最大の項目）。保存で片方を外して読むときに戻す形にできるが、2か所が同じオブジェクトを指すようになり、その場で書き換えるところがあると動きが変わるので、作りを確かめてから。
3. **Web の配布が一人用とオンラインで1つの HTML**（2.84MB、gzip 830KB）。オンライン用に分ければ半分近くになるが、配布の形の変更なので持ち主の判断。
4. **アプリはまだ「オフの成長」のまま**（`ProceduresScreen.kt`・`OffseasonGrowthCard`）。Web は「その年のまとめ」に替えたので、アプリも `yearSummary` を描く形に移すか。移したらビューの `lastOffseason.gains`（名簿全員の能力の差を1年中送っている）を `year`・`departed` だけに縮められる。
5. **NPBドラフトの発表のカードをアプリにも出すか**（いまは Web だけ）。
