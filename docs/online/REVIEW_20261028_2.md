対象は前回修正 `2e4c757` 以降。編集開始から保存完了までの状態、同一ログインの複数タブ、通信失敗、保存世代の整理、バックアップ復元後の画面を重点的に確認した。

## 指摘と修正

|優先度|再現条件・影響|修正|
|---|---|---|
|高|編集中に同じログインの別タブが提出・編成を保存。更新ボタンや定期取得で全体revisionだけ新しくなると、古い入力で新しい保存内容を上書きできた。|編集開始時の提出・編成を送信し、APIで現在の対象と比較して競合を拒否。PCは入力を残して保存案の再取得を提供、スマホの確認は最新の保存案へ追従する。相手球団だけの更新では対象が同じなら保存できる。|
|中|保存応答を待つ間も選択入力を変更できた。成功後の再取得によって送信後に入力した変更が失われる。|保存中はフォーム全体を無効にする。|
|中|保存先ポインタを読んでからオブジェクトを取る間に複数世代が更新・整理されると、旧ファイルの404で読取りが失敗。|HTTP 404、またはStorage RESTのHTTP 400かつ本文の不存在コードで、保存先が変更された場合だけ、最新の一式を一度取得し直す。現行ファイルの欠損は503のまま保持する。|
|中|標準案の初回取得が失敗すると同じ手続き内では再試行できない。手続きが変わった応答を旧画面が採用する可能性もある。|再取得ボタンと手続きIDの照合を追加。ゲートウェイ等の非JSON応答も日本語の再確認メッセージにする。|
|中|復元や選手数・結果件数の減少後に、存在しないページやお知らせの選択が残って空表示になる。|ページを有効範囲に戻し、削除済みのお知らせは先頭の有効な項目へ戻す。スマホの表示件数は維持する。|

## 回帰検証

- `check:online`：操作APIの編集競合と他球団の更新、Storageの旧世代削除と現行欠損を含む。
- `check:online:ui`：専用の空のFileStoreと実APIで二人分の操作。同じログインの別タブ、保存中の入力停止、競合後の再取得、旧端末の拒否、実試合結果、320〜767px幅を確認する。
- `check:online:auth-ui`：配布HTMLとAuth fixtureによる既存の認証競合検証。
- `check:online:edit-ui`：配布HTMLとAPI fixtureで標準案の再試行、非JSON応答、手続きIDの不一致、保存中入力、スマホ確認の更新、名簿・お知らせの縮小を確認する。
- UI fixtureの応答待ちは期限付きにし、到達しない場合にCIが無期限で待たないようにした。
- 既存検査は `check:full`、実試合による次年度までの進行は `check:online:season`、配布物は `build` で確認する。

ローカル実行結果: 上記の `check:full`、`build`、`check:online:season`、3種の画面検査、`git diff --check` はすべてPASS。実通年は243日を消化し、2年目開幕まで到達した。画面は独立したChromeプロフィールで確認した。

## 検証の境界

クラウドStorage/Authの通信はfixtureであり、Supabaseの実権限・Vercelの定期起動・実スマホでの成功を示さない。これらはアカウント設定後の受入として保留。ローカルの実API操作と、配布HTMLの通信fixture検証を分けて扱う。

既存の未追跡 `output/` と別件の成績資料は変更・コミット対象に含めない。

Storage RESTのエラー判定は [公式エラーハンドラ](https://github.com/supabase/storage/blob/master/src/http/error-handler.ts) と [不存在コードの定義](https://github.com/supabase/storage/blob/master/src/internal/errors/codes.ts) を確認した。HTTP 404・HTTP 400の新旧不存在形式をfixtureで検証し、権限不足や不正要求を再取得対象にしない。
