# オンライン版の起動・運用

## 現在の到達点

PCの球団閲覧・事前采配・観戦は [PC_GAMEPLAY.md](PC_GAMEPLAY.md) を参照。観戦記録は追加後の試合から保存する。

2部制12球団の独立リーグ。人間は1〜12人で、残りはCPUが持つ。構造・時間軸・参加の設計は [PYRAMID_LEAGUE.md](PYRAMID_LEAGUE.md) を参照。
PCは左ナビで今日・試合・選手・編成・手続き・管理を分ける。既存PC版と同じsurface/accentを使用する。
編成は「詳しい編成を開く」で一人用のロスター管理画面（打順のドラッグ＆ドロップ・守備配置図・投手の役割枠）をそのまま使う。
初期編成とトライアウトは、左に獲得予定・右に候補（360人）を置いて、守備位置・並べ替え・名前で絞って指名する。
名簿が成り立たない希望（野手8人・投手1人・捕手1人を満たさない）は、提出する前に画面で知らせる。
スマホはホームから画面を選び、戻る・ホーム・メニューを下部の小さい操作欄に集約する。ブランドヘッダとカードの外枠は省き、選手一覧は画面高に応じた人数を表示する。保存/決定ボタンは下部操作欄のすぐ上に配置する。
既存の一人用モードとは保存・画面・進行を分離している。
途中参加は招待コードで行う（管理者が「管理」画面で発行する）。トレード、既存セーブの移行、選手エディット、監督移籍、キャンプの副練習・派遣・球種習得は対象外。

外部アカウントが不要な実装とローカル受入は完了。Supabase / Vercelの実接続、SQL適用、RLS検証、定期実行、実機受入は未実施。
公開用設定がない環境はエラーで停止し、開発用認証へフォールバックしない。

## ローカルで二人分を試す

Node 20以上で `npm ci` を実行し、端末を二つ開く。

```sh
npm run dev:online
```

```sh
npm run dev
```

`http://localhost:3000/online` を開く。一人用タイトルの「オンラインペナント」からも開ける。
プレイヤー1でリーグを作成し、別のブラウザプロフィールかシークレットウィンドウでプレイヤー2として入る。
同じブラウザの別タブでは認証保存領域が共有されるため、二人の検証には独立したプロフィールを使う。

両者が初期編成を決定し、キャンプを決定すると開幕する。
ローカルの管理者にだけ「検証用：1日進める」を表示する。本番にはこの操作を提供しない。
共有状態は `.online-data/league.json.gz`。一人用のIndexedDBやセーブスロットには書き込まない。
ローカルAPIは127.0.0.1限定・単一プロセス専用。本番運用に流用しない。

## 自動検証

```sh
npm run check:full
npm run build
npm run check:online:season
```

既存の多年次検査は試合を省略する。オンライン通年検査は実試合を毎日消化し、243日を経て2年目の開幕まで進む。
外部通信のfixture成功は、Supabaseの権限やVercelでの動作成功を保証しない。

ブラウザ検査には**空の専用保存先**を指定してAPIを起動する。通常の検証リーグを操作しない。
既存のAPIと同時には起動できないので、`dev:online` を止めてから以下を実行する。
Viteは3000番の既存サーバーを利用できる。

```sh
ONLINE_DISABLE_TIMER=1 ONLINE_DATA_FILE="$(mktemp -d)/ui.json.gz" npm run dev:online
```

別端末から実行する。

```sh
npx playwright install chromium
npm run check:online:ui
npm run check:online:auth-ui
npm run check:online:edit-ui
npm run check:online:label-ui
```

インストール済みChromeを使う場合は `PLAYWRIGHT_CHROME_CHANNEL=chrome npm run check:online:ui`。
CIも同じ検査を実行し、スクリーンショットを保存する。認証競合と編集復帰の画面検査は配布HTMLとAPI/Authのfixtureを使う。
ブラウザ検査は初期編成・二人の決定・キャンプ・編成保存・スマホ操作・旧端末拒否・試合結果・320〜767px幅を確認する。

## 外部アカウント設定後の作業

⚠ 作者の本番環境について、**実際に構築したときの固有情報とつまずいた点**は
[PRODUCTION_SETUP.md](PRODUCTION_SETUP.md) に分けてある。こちらは手順の一般形。

1. SupabaseプロジェクトとVercelプロジェクトを作成する。課金・プラン変更はこの実装では行わない。
2. Supabase Authに二人分のメール・パスワードのユーザーを作成する。招待受付・公開サインアップは提供しない。
3. `supabase/migrations/202610280001_online.sql` を適用する。新設テーブル・RPCはservice_roleだけ、Storageバケットはprivate。
4. `.env.example` の値をVercelのサーバー環境変数へ設定する。`ONLINE_MEMBER_1`が管理者。`VITE_`を付けて公開しない。
5. Vercelへこのブランチをデプロイする。Node関数のFluid Computeと300秒上限を確認する。
6. まずCronを無効のままログイン・初期編成・二人の決定を検証する。
7. Supabaseでpg_cron・pg_netを有効にし、VaultへURLとCron秘密値を保存する。`supabase/cron.example.sql` を参照して設定する。Cronの時刻はUTC。
8. 次の公開環境受入を実行する。受入前の本運用開始は保留する。

## 公開環境で必要な受入

- 未認証・非参加者・相手球団・旧端末・古いrevisionの更新が拒否される。
- anon/authenticatedキーからテーブル、RPC、private Storageを直接取得・更新できない。既存の広いStorageポリシーも確認する。
- 相手の未確定の希望リスト・契約案をAPI応答に含めない。
- 別の関数インスタンスから同時操作しても一方のみ成功する。期限切れリースで公開できない。
- Cronが1回で1日だけ進む。同じ通知の再送・停止中の通知・決定待ち中の通知で二重進行しない。
- 日次の背景球界計算とStorage通信が関数の時間・メモリ・転送量の枠内に収まる。
- 認証トークンの更新、端末切替、通信断からの再読込を実サービスで確認する。
- 停止・バックアップ・復元後に試合成績や両者の提出を二重適用しない。
- iOS Safari / Android Chromeの実機でも閲覧・打順変更・決定を確認する。

## 進行と障害復旧

毎正時に1ターン進む（1ターン＝1時間＝1試合日）。24ターン×7日＝168ターンで1シーズン。
イベント決定待ち・管理者の停止・エラー中は進まない。再開は次の未来の枠から。
15分を超える遅延通知は停止扱いにし、空白期間を自動消化しない。
Cronの例は通知欠落や処理中に備え、各枠の5分後・10分後にも再送する。進行は予定時刻を確認して1枠1回に限定する。
プレーオフは引き分けで未決着なら翌日に再試合を追加し、2勝先取の条件を維持する。10月20日までに決着しない異常時は停止する。

エラー時は最後の正常なスナップショットを残し、状態を確認して管理者が再開する。
ブラウザの通信失敗だけでは処理の成否を判断できないため、最新状態を再取得する。
操作IDの再送は重複適用せず、履歴の保存範囲を超えた古い操作はrevisionで拒否する。

DBには小さい画面用データと公開ポインタ、private Storageには世界・提出・操作履歴・端末情報をまとめたgzipを置く。
通常のStorage世代は現在＋直前2世代。公開失敗や応答喪失で残る未参照ファイルは自動削除しない。
容量が増えた場合は処理を停止し、現行ポインタと直前2世代以外の未参照ファイルを管理者が確認して削除する。

管理画面のバックアップは同じ共有状態内の退避1件。最新バックアップで置き換わる。
同じStorageの破損・アカウント喪失対策には独立した手元のコピーも必要。
進行を停止し、サーバー用の `.env` を用意した管理端末で次を実行する。

```sh
node --env-file=.env tools/online-backup.mjs export /安全な保存先/world.json.gz
```

既存ファイルは上書きしない。退避ファイルにはゲームと参加者情報が入るためGitや公開先へ置かない。
手元のファイルから復旧する場合も、現在のリーグを停止する。

```sh
node --env-file=.env tools/online-backup.mjs restore /安全な保存先/world.json.gz
```

復元後は全端末で再ログインし、日付・順位・提出内容を確認してから再開する。
DBのポインタが失われた場合も、同じ二人の設定と新設テーブル・privateバケットを用意して復元できる。
ゲームエンジンのバージョンが異なる場合は拒否する。将来のルール変更時は明示的な移行が必要。

## コストと運用上の制限

外部サービスの無料枠は実際のプロジェクト設定で確認する。常時起動のサーバー、WebSocket、Redis、常時ポーリングのCronは使わない。
画面は表示中に約1分ごと、Cronは1日7枠（各枠は再送を含め最大3回の通知）。画面APIは全世界の巨大なスナップショットを転送しない。
ただし認証・更新・背景球界処理には通信と計算が必要で、無料運用を保証するものではない。
Supabaseの休止・容量上限・Storage/DBの復旧手段、Vercelの実測時間を公開前に確認する。

参照: [Supabase Storage権限](https://supabase.com/docs/guides/storage/security/access-control)、[Database Functionsの権限](https://supabase.com/docs/guides/database/functions)、[Cron](https://supabase.com/docs/guides/cron)、[pg_net](https://supabase.com/docs/guides/database/extensions/pg_net)、[Vercelの実行時間](https://vercel.com/docs/functions/configuring-functions/duration)。
