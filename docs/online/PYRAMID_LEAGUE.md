# 多人数ペナント（2部制・12球団）の設計

当初は7リーグ・42球団で設計し、保存の容量で2部制に縮めた（下記）。

⚠ **段階1〜3は実装済み**（参加者モデル・2部制12球団と昇降格・毎正時24ターンと
締め切り）。残りは段階4（場面別の采配）と段階5（ストーブリーグ）。
この文書は設計と実測の記録で、済んだ項目にも**なぜそう決めたか**を残している。

## 決まっていること

### 時間軸

| | |
|---|---|
| 1試合 | 毎正時。1日24ターン |
| 試合 | **月曜〜金曜の5日間＝120ターン（うち20は休養日、100試合）** |
| 土曜 | **ストーブリーグ**（契約更改・トライアウト・オフシーズン） |
| 日曜 | **キャンプ・編成** |
| 月曜0時 | 新シーズン開幕 |

⚠ **120は6球団の総当たり（1巡5節）に割り切れる**。実測で、
144ターンだと28.8巡で最後の1巡が途中で切れ、
「相手によって28試合と29試合」「ホームが71〜74」とばらついた。

⚠ **6ターンに1回は休養日にする**（`REST_EVERY`）。`recoverAllPitcherFatigue` は
「その日出場した選手は回復させない」ので、毎ターン試合があるとレギュラーの疲労が
**一度も回復しない**。実測で、20試合の時点で一人用が平均24（最大97）なのに対し
オンラインは平均104（最大281）まで積み上がり、疲れた打者は打てないので
**本塁打が一人用の1/5**（1試合あたり 0.68 → 0.13）になっていた。
休養日を入れると 0.46 まで戻り、打率・防御率・三振率もほぼ一致する。
120ターン中100試合で、どの相手とも20試合・ホーム50/ビジター50。

⚠ **球団の格付けを当て直すこと**。`ensureUserIndependentLeagueTagged` は
プリセット定義と**名前で**照合するので、その場で作った球団名は全部 'D'（最弱）に
なる。トライアウトの候補の質はこの格付けで決まるため、リーグ全体の選手が
弱くなっていた（実測でミート43.9→36.8、制球44.5→36.6）。

### 一人用との突き合わせ（20試合・12球団・同じ初期メンバーセット）

| | 一人用 | オンライン |
|---|---|---|
| 打率 | .229 | .232 |
| 1試合あたり本塁打 | 0.43 | 0.46 |
| 防御率 | 2.95 | 2.85 |
| 三振率 | 22.2% | 21.1% |
| 野手の疲労（平均） | 21 | 35 |

⚠ **疲労の最大値だけまだ開いている**（76 対 229）。出ずっぱりの数人が
休養日の回復量を上回って積み上げている。平均と集計値は揃っているので
当面は許容するが、休養の間隔（`REST_EVERY`）か代役の出し方で詰める余地がある。

⚠ **人の球団は特に積み上がる**。CPUは毎試合疲労を見て打順を組み直すが、人の球団は
保存した打順のまま出続けるので、ブラウザでの実測で遊撃手の疲労が8月に396まで達し、
打撃がほぼ0になった。いまは疲労80以上の野手を、その守備位置を守れる元気な控え
（疲労40未満・適性60以上）とその日だけ入れ替える（`server/dailyLineup.mjs`）。
保存した打順は変えない。守れる控えが居なければ休ませない。

### この突き合わせは検査になっている（`online-parity-check`）

同じ球団数・同じ試合数・**同じ初期メンバーセット**で両方を動かし、打率・本塁打率・
防御率・疲労・能力・名簿の構成を並べて許容幅に収まるか見る。上の3つの不具合は、
どれも**個々の部品の検査はすべてPASSしたまま**すり抜けていた。試合の処理は
正しく、**世界の作り方**が違っていたため。

⚠ **比較で捕まるのは「オンラインと一人用の食い違い」だけ**。両方が同じ
エンジンを使うので、**共通の退行は比較では捕まらない**（両方が同じだけ壊れる）。
実際に「野手が疲労回復しない」を故意に入れたら素通りした。初期メンバーセットの
格の段差を壊して全体を弱くしたときも素通りした（一人用側も同じセットから組むので
両方が同じだけ下がる）。そのため、日程に休養日があることや格付けが一致すること、
セットの能力の水準（`online-pack-check`）は**別の検査**で数字を押さえている。

⚠ **名簿の作り方を変えたら、一人用側の組み方も合わせること**。オンラインを
初期編成からセット選択へ変えたとき、一人用側が初期編成のままで制球の平均が
48.2 対 54.2 とずれて落ちた。土台がずれていれば試合の処理が正しくても落ちる
（そして正しく落ちている——比較になっていないのだから）。

⚠ **比較の土台をオンライン側から取らないこと**。一度「一人用に渡す格付けを
オンラインの世界から読む」と書いたせいで、格付けが 'D' に落ちる不具合に対して
一人用側にも 'D' を渡してしまい、**間違いを基準にした比較**になって素通りした。
あるべき値（生成時の定義）と突き合わせること。

⚠ **操作IDに乱数を使わないこと**。進行の乱数は操作IDから作られるので
（`seeded(league, 'day:' + operationId)`）、毎回違うIDだと結果が揺れる
（実測で打率が .227〜.245）。固定すれば完全に再現する。

⚠ **平均だけ見ないこと**。12球団の平均は1球団が壊れてもほとんど動かない。
人の球団だけ野手9人（他は14人）でも平均13.6で埋もれた。最小・最大も見る。

1回およそ2分かかる。`npm run check` に入れてある。

⚠ **締め切りで自動決定する**。待ち続ける設計だと1人が決めないだけで
全員の週が止まる。締め切りを過ぎたら未提出の人に既定案（`defaultPhasePlan`）を
当てて先へ進む。

⚠ **締め切りが曜日合わせを兼ねている**。ストーブリーグは日曜0時、
キャンプは月曜0時が締め切りなので、全員が早く決めても次の開幕は
月曜0時まで来ない（曜日がずれない）。

⚠ **開幕前の手続きにも締め切りを置くこと**。以前は「最初の1回くらいは全員を
待とう」と設けなかったが、**1人が決めないだけでリーグが永久に止まった**
（実際に開幕前の日付のまま何日も動かなくなった）。時間による進行が絶対で、
決めていない人は標準案で押し通す。初期メンバー選択は土曜扱い（締め切り日曜0時）に
してあり、続くキャンプが月曜0時に締め切られて**月曜開幕**になる。

⚠ **手続きは1回の定期処理につき1つずつ解決する**。次の手続きの締め切りは
「開いた時刻」から数えるので、まとめて片付きはしない。止まらないことが大事で、
急いで進めることが目的ではない。

### 画面の分け方

左メニューは3つのまとまりに分ける。⚠ 以前は「今日/試合/選手/編成/手続き」が
平らに並ぶだけで、どこに何があるか辿れなかった。

| まとまり | 中身 |
|---|---|
| **情報** | 自チーム情報 / 選手成績 / 能力ランキング / 試合結果 |
| **ロスター管理** | スタメン設定 / 投手起用 / 守備分析 / 方針・采配 |
| **手続き** | 現在の手続き / 移籍・解雇 |

ロスター管理の3つは、移植した一人用画面の**中のタブ**へ直に入る
（`OnlineLineup` に開く位置を渡す）。

⚠ **移植画面は左メニューを覆わないこと**（`.online-lineup-portal` の `left`）。
全画面にしたら、スタメン設定から投手起用へ移れなくなった。

ホーム（既定の画面）には3つ出す。数字はすべてサーバーが作る
（`server/leagueBoard.mjs`）。画面で計算し直すと出どころが2つになる。

1. **2部制の順位表** — 人が持つ球団には名前を括弧で添える。
   ⚠ CPUには付けない。⚠ 呼び名が球団名と同じときも付けない
   （参加時の既定が球団名なので「湘南サンズ（湘南サンズ）」と2回並ぶ）
2. **今後の日程** — 対戦相手と先発予定。⚠ ローテを回して出すこと
   （毎回同じだと1人が全試合に先発する予定になる）。予定であって確定ではない
3. **リーグ上位** — 各項目のベスト5。⚠ 率の項目は**規定に届いた選手だけ**
   （混ぜると3打数2安打の控えが打率1位になる）

⚠ 球団名とプレイヤー名は「自チーム情報」から**後から変えられる**。
以前は参加のときしか付けられず、リーグを作った管理者には機会すら無かった。

### 検証モード

作っている間は、毎正時を待っていると試せない。管理画面の**検証モード**をONに
すると、管理者だけ「手続きをいま締め切る」「1ターン進める」「24ターン進める」が
使える。⚠ **遊び始めたらOFFに戻すこと**（好きな時に進められるのは公平ではない）。
環境変数 `ONLINE_ALLOW_STEP` でも立つが、そちらは再デプロイが要る。

⚠ **1ターン＝実時間1時間＝ゲーム内1日（＝1試合）**。「1日進める」と書くと
どちらの1日か分からないので、画面にはターン数とゲーム内の日数を併記する。

⚠ **以下の3つが揃って、はじめて週の割り当てが成り立つ**（2026-11 に直した。
それまでは1年に約240ターンかかり、曜日がずれていた）。

- **シーズン後の空き日はまとめて進める**（`advanceLeagueDay`）。レギュラーシーズンは
  4/1〜7/29 の120日で終わるが、プレーオフは10/10、契約更改は11/9。この間を
  1時間に1日ずつ進めると約100時間かかっていた。いまはレギュラーシーズンが
  終わったあとの「試合の無い日」を1回の進行で最大60日ぶん進める。
  ⚠ 日付を飛ばすのではなく**1日進行の繰り返し**（間の大会・ドラフト・手続きの判定を落とさない）。
  ⚠ レギュラーシーズン中の休養日はまとめない（1ターンとして数える設計）。
- **開幕は月曜0時**（`seasonStartAt`）。キャンプが早く決まっても次の月曜0時まで待つ。
  月曜に入ってから決まったとき（締め切りの自動決定を含む）は次の正時から始める。
- **遅れて開いた手続きは短い猶予で締める**（`LATE_PHASE_GRACE_HOURS`）。契約更改が
  日曜0時の締め切りまでかかると、続くトライアウトは日曜に開く。そのまま「次の日曜0時」を
  締め切りにすると7日後になるので、トライアウト12時間・オフシーズン4時間で締める。
  ⚠ 猶予の長さは仮決め。土曜の中で3つをどう割るかは運用を見て決め直してよい。

実測（2人・既定案・キャンプを火曜12時に決定）：月曜0時開幕 → 金曜22時に
レギュラーシーズン終了 → 土曜1時に契約更改 → 日曜1時にトライアウト（13時締め）→
日曜14時にオフシーズン（18時締め）→ 日曜18時にキャンプ（月曜0時締め）。
1年が124ターン＋手続きで回る。

現行は「1枠進むと1日進む」で1日7枠。これを**1日24枠・毎正時**にし、
`gamesPerSeason` を 144 にすれば時間軸は乗る。日曜だけ、試合ではなく
ストーブリーグのフェーズへ割り当てる。

⚠ 現実の曜日とゲーム内フェーズを対応させる必要がある。現行は
ゲーム内のカレンダー（4月〜10月）で判断しており、曜日は見ていない。

### リーグ構造（2部制・12球団）

```
   1部   （6球団）
   2部   （6球団）
```

| 階層 | 昇格 | 降格 |
|---|---|---|
| 1部 | — | **最下位** → 2部 |
| 2部 | **1位** → 1部 | — |

1つ降りて1つ上がるので**出入りが釣り合う**（検査が自動で確かめる）。

⚠ **7リーグ42球団は見送った。** 保存の容量が無料枠に収まらなかった（下記の実測）。
構造は `PYRAMID_LEAGUES` の表1つで決まるので、容量の目処が立てば広げられる。

⚠ **降格は「下から数える」こと**（`RELEGATION_FROM_BOTTOM`）。
「6位」と上から書くと、1リーグの球団数を変えたときに最下位でない球団が落ちる。

### 容量（実測）

毎ターン世界スナップショットを全部書き直す作りなので、
**記録が増えるほど1回の書き込みが重くなる**。

| 構成 | 球団 | 1シーズンの試合 | 月間書き込みの目安 |
|---|---|---|---|
| **2部制（採用）** | 12 | 864 | **約1.6 GB** |
| 3リーグ | 18 | 1,296 | 約2.4 GB |
| 4リーグ | 24 | 1,728 | 約3.2 GB |
| 7リーグ | 42 | 3,024 | 約5.5 GB |

⚠ 観戦リプレイ（1球ごとの記録）は**既定で保存しない**。
1試合218KBのうち182KB＝84%を占め、42球団では1シーズン670MBとなって
`JSON.stringify` の上限（約512MB）を超えた。成績だけなら1試合30KB。
球団数の少ないリーグで観戦したいときは `ONLINE_RECORD_REPLAY=1` で有効にできる。

**2部制の実測**: 1試合30KB / 1シーズン25MB / gzip後2.3MB。

⚠ **上の見積もりは試合結果の重複を数えていなかった**。2026-11 に1年通しで測ると、
契約更改の時点で保存が192MB（gzip 24MB）あった。試合結果に両球団の名簿の写し
（1試合約100KB）が入り、しかも `season.results` と `season.schedule[].result` の
2か所に入っていたため。いまは保存前に写しを外している（`slimStoredResults`。
個人成績は記録 `records` に別にある）。外したあとの実測は、2年目のキャンプ時点で
77MB（gzip 7.2MB）。残りの大半は世界の球団（CPU以外の約550球団、約47MB）と
記録（約22MB）で、ここを減らすのは今後の課題。

### 参加者

| | |
|---|---|
| 人数 | **1〜12人**。随時追加できる |
| 入口 | **アカウントを持っている人は誰でも**。アカウントは管理者が作る |
| 残りの球団 | CPU |
| 途中参加 | **2部（最下層）から。CPU の最下位が弾かれる** |

⚠ **球団名は「表示名」で持つ**（`displayName`）。内部名（`name`）は
`TEAMS_DATA` のキー・日程の対戦相手・順位表・記録の選手キー（`onlinePlayerId`）
まで貫いているので変えられない。参加した人が付けた名前は、投影の `teamLabels`
（内部名 → {表示名, 短縮}）で渡して画面だけ差し替える。
これが無かったとき、名前を付けても画面には引き継いだCPU球団の名前が出ていた。

⚠ **ここが最大の変更点。** 現行は参加者を Vercel の環境変数
（`ONLINE_MEMBER_1` / `ONLINE_MEMBER_2`）で決めており、
1人追加するたびに環境変数の編集と再デプロイが要る。42人には使えない。
`createLeague` にも `members.length === 2` の強制がある。

**参加者はリーグのデータ側で持つ**形に変える。環境変数に残すのは
「誰が管理者か」だけでよい。

⚠ `docs/online/README.md` に「**途中参加**は対象外」と書かれているとおり、
途中参加は未実装。今回これを実装する。

### 球団

**全球団（いまは12）ランダム生成**。プロ扱いで、独立リーグと同じ形式。

既存の `INDEPENDENT_LEAGUES` には **26球団**しかないので、
42球団を生成する仕組みを作る。人間が参加した球団は**本人が命名**して上書きする。

### 采配

**自動**。人は試合に立ち会わない（毎正時に進むため）。
代わりに**場面ごとの方針**を事前に設定する。

土台は `src/online/tactics.js` にある。

- 打撃方針 / 投球方針 / 走塁方針 / 守備方針
- 先発の役割（完投型・勝ち権利型・ショートスターター・オープナー等）
- 中継ぎの役割（ロングリリーフ・セットアッパー・守護神・ワンポイント等）
- 球数制限・ダメージ基準・バント/代打/守備固めの積極度

これを**条件付き**へ拡張する（「7回以降・1点差なら」「対左投手なら」など）。

### ストーブリーグ

日曜に行う。2つの方式を持つ。

**1. オークション**

複数人が入札し、時間内の最高額が落札。

**2. 個人間トレード（交渉制）**

```
提示側: 欲しい選手を指定 ＋ 出す選手・金銭相当を提示
  ↓
相手が時間内に了承            → 成立
相手が条件を変えて再提示      → さらに双方の了承が必要
```

不成立になる条件:

- 時間内に成立しなかった
- 目当ての選手が**先に他で決まった**
- **資金が足りなくなった**（他の取引で使った等）

⚠ 再提示があるので、単純な「提案→承諾」ではなく**交渉の往復**になる。
どちらが最後に了承したかを記録し、条件が変わるたびに同意をやり直す。

⚠ `README.md` に「トレードは対象外」とあるとおり、これも未実装。

## 実装の順番

一度に全部は作れない。**動くものを確かめながら積む**。

| 段階 | 内容 | 規模 | |
|---|---|---|---|
| **1** | 参加者モデル（データ側で管理・1〜12人） | 大 | 実装済み |
| **2** | 球団の生成と2部制・昇降格 | 中 | 実装済み |
| **3** | 時間軸（毎正時24枠・月〜金120試合・土日の枠確保） | 小 | 実装済み |
| **4** | 場面別の采配設定 | 中 | |
| **5** | ストーブリーグ（オークション・トレード） | 大 | |

段階の外で、**一人用のロスター管理画面をオンラインへ移植した**
（`src/online/OnlineLineup.jsx`）。オンライン側の編成欄は打順を↑↓で動かすだけで、
守備位置の組み合わせも投手の役割も見えなかった。移植したことで、
ドラッグ＆ドロップ・守備配置図・役割枠・自動編成がそのまま使える。

### 開幕前の名簿は「初期メンバーセット」から選ぶ

開幕前の手続きは**20セットから1つ選ぶ**形にした（`src/online/rosterPack.js`・
`src/online/PackSelect.jsx`・フェーズ名 `pack_select`）。以前の初期編成
（360人の希望リスト）は置き換えて、コードから消した。

1セットは**24人**で、どのセットも構成と格付けが同じ：

| | |
|---|---|
| 構成 | 投手11・捕手2・内野5・外野4・投手本職の二刀流1・野手本職の二刀流1 |
| 格付け | A2・B10・C12 |
| 年齢 | 19〜24歳 |

⚠ **どのセットを選んでも不利にならないようにする**。選ぶ時点では中身しか
見えないので、合計の力がばらつくと「当たりのセット」を引いたかで勝負が決まる。
24の枠ごとに20人作って評価順に並べ、**そのときの合計が少ないセットから順に**
配る。枠ごとに蛇行（1→20→1）で配っていた頃は開きが7.2%残り、
走っている合計を見る形にして1%前後になった。

⚠ **格付けの段差は `RANK_LEVEL_SHIFT` を流用しない**。あれはA=0・B=-8・C=-16 で
**チームの格をチーム全体に当てる**表なので、選手の格に当てると能力が全体に
下がり、表示がほぼ全員Fになった。中心をBに置く別の段差を使う
（`PACK_RANK_SHIFT`）。投手の制球の平均で、流用すると43前後・正しい段差で49前後。

⚠ **格付けを枠の順に配らない**。構成は投手から並んでいるので、順に配ると
Aの2人がどちらも投手になり、**野手にAが1人も居ない**セットができた（実測）。
少ない格から等間隔に置いて24枠へ散らす（`spreadRanks`）。

⚠ **配ったら打順と投手起用まで作ること**（`refreshTeamPlan`）。名簿を渡すだけでは
試合が組めない。付け忘れたときは打順が空のまま開幕し、打順の入れ替えが例外で
落ちた（実測）。

⚠ **同じセットは1球団だけ**。選手のidと名前が重複すると、記録がどちらの選手の
ものか分からなくなる。取り合いになったら**球団名の順**で決める（乱数で決めると
同じやり直しで違う結果になって再現しなくなる）。選ばなかった球団には残りを順に配る。

⚠ **配り終えたらセットを捨てる**（`delete league.packs`）。20×24＝480人ぶんを
保存に抱えたままにしない。

シーズンが終わってからの流れは、契約更改（解雇する選手を選ぶ）→ トライアウト
（解雇された選手＋新たに独立リーグを目指す選手から選ぶ）→ キャンプ → 新シーズン。
開幕前のセット選択はこの1回だけで、2年目以降はトライアウトが名簿を埋める。

⚠ **年末のトライアウトの候補は12球団で実測120人**。初回だけ `teamCount * 30` を
生成していたが、オンラインに初回トライアウトは無くなったので、常に実在プール
（高卒・大学4年・FA）から引く。空の名簿を12球団ぶん埋めるには足りないので、
名簿が空の状態でトライアウトを開かないこと。

**トライアウトの画面は作り直した**（`src/online/TryoutPlanner.jsx`）。

⚠ **こちらは移植できない。** 一人用は「順番が回ってきたら1人選ぶ」生のドラフトで、
オンラインは非同期なので「希望リストを1回出す」。画面の中身以前に操作の型が違う。

候補は1本のリストで扱える数ではない（開幕前の初期編成だった頃は実測360人、
年末のトライアウトは12球団で120人）。既定案は候補全員に順位を付けた状態で、
以前はそれを1本のリストにして ↑↓ で並べ替えさせていた。
300番目を1番に上げるには299回押すことになる。
作り直した画面は、左に獲得予定（並べ替える）、右に候補（守備位置・並べ替え・
名前で絞って指名する）を置く。

⚠ **`rankedIds` からは誰も取り除かない**。サーバーは上から見て空いている人を
取るので、全員残しておくと競合したとき繰り上がる。「控えへ」は末尾送りにする。

⚠ **希望順だけで取らないこと**（`ROSTER_TARGETS`）。候補の38%が投手なので、
順番どおりに取ると自分の番が回る頃には投手ばかりが残る。実測で、人の球団だけ
**投手15人・野手9人**（控えゼロ）になり、CPUは全球団が投手10・野手14で
揃っていた。野手9人では代打も守備固めも出せず、レギュラーが全試合に出続けるので、
成績の出方が一人用と別物になる。目標（投10・捕2・内6・外6）を満たした区分は
飛ばして次の希望へ進む。画面の「獲得予定」も**同じ関数**で出すこと
（`plannedPicks`）。片方だけ直すと、並んでいる顔ぶれと実際に取る顔ぶれが食い違う。

1〜3で「遊べる最小形」。4と5で深くなる。

⚠ **段階1が土台。** これが無いと1人でも遊べない（現行は2人必須）。

## 進め方の制約

### 既存のリーグは作り直しになる

参加者モデルを変えるとリーグデータの形式が変わる。
`assertLeagueVersion` が `schema` と `engineVersion` を照合して古い形式を拒否するので、
**既存のリーグは消して作り直す**。

### main に入れた瞬間に公開される

`main` は本番へ自動デプロイされる。作りかけを main に入れると遊べなくなる。

**ブランチで進め、完成してから一度に main へ入れる。**
Vercel の Preview URL を使えば、本番を止めずに確認できる。

### 影響範囲（実測）

`members` が流れている箇所:

- サーバー9ファイル（`leagueEngine` / `leagueService` / `projection` / `http` /
  `lineupCommand` / `production` / `dev` / `archiveIndex` / `storage/supabaseStore`）
- 画面3ファイル（`LeaguePanels` / `PlayerPerformance` / `TeamRoster`）
- ハーネスの検査10本以上

**検査が10本以上あるのは有利。** 壊したらそこで止まる。
