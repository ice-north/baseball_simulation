# 総合監査の手順

「総合監査して」と頼まれたときの手順。前回の記録（`docs/audit/` の最新）から続けて行う。

## 0. 準備

- 確認のコマンド（`package.json`・`CLAUDE.md`・`mobile/README.md`・`.github/workflows/`）:
  - Web: `npm run build`、`npm run check`（lint を含む）、`npm run check:progression`、`npm run check:online:season`（約2〜3分）
  - 画面: `npm run check:ui`、`check:online:ui` ほか `check:online:*-ui`（Playwright。手元の Chromium が版と合わないときは `PW_CHROMIUM` で指定）
  - アプリ: `mobile/` で `node tools/gen-tables.mjs --check`・`node tools/expect-logic.mjs --check`・`./gradlew -PsharedOnly :shared:jvmTest`（SDK があれば `:androidApp:testDebugUnitTest`）
- 型検査は無い（JavaScript）。Kotlin はビルドが型検査を兼ねる。
- エラーログ: リポジトリ内には集める仕組みが無い。本番は Vercel の関数ログと Supabase のログ（`docs/online/PRODUCTION_SETUP.md`）。見られないときは飛ばして記録に書く。
- 決まりの文書: `CLAUDE.md`（変更時の不変条件）、`仕様書.md`・`開発ガイド.md`・`ゲームフロー.md`、`docs/online/*.md`、`mobile/README.md`（サーバーとの約束）。過去のレビュー記録は `docs/online/REVIEWS.md`・`docs/online/REVIEW_*.md` と `docs/audit/`。

## 1. 範囲

前回の記録の「範囲の終わりのコミット」から既定ブランチ（main）の先頭まで。記録が無ければ直近1週間。新しいコミットが無ければ「変更なし」とだけ返して終える。

## 2. 基準の確認

最初に確認を全部回す。最初から落ちているものも監査の対象に入れる。

## 3. エラーログ

前回以降の分を「操作×本文の種類」で件数にまとめ、本物の不具合は直す対象に入れる。

## 4. レビュー（読むだけ）

範囲のコミットが触ったファイルで3〜5組に分け、組ごとにサブエージェント1人（並列・編集しない・同時に10人まで）。見る順:

1. 不具合（具体的な入力・状態でどう壊れるか、ファイル:行つきで言えるものだけ）
2. 決まりの文書との食い違い
3. リファクタ候補

必ず見る型: 保存データの形・上限を片側だけ変えた／2つのシステム（フロントとサーバー、アプリとサーバー）の取り決めが片側だけ変わった／機能を移した・消した後の呼び残しや消し過ぎ／裏の処理（タイマー・自動リトライ・外部API）が止まらない・二重に走る・失敗で連打する。前回までの記録にあるものは再報告しない。

## 5. 修正

指摘をファイルが重ならないように分け、worktree で並列に直す。直す前に再現し、違えば直さず理由を残す。直したら回帰テストを足す（`tools/sim-harness/` の検査、アプリは `jvmTest`）。テストを飛ばす・待ち時間を延ばすだけの直しはしない。

## 6. 小さな判断

決まりに無い見た目・使い方の判断は、案とおすすめを決めておすすめで実装する。1問1コミットで件名の頭に Q1・Q2… を付け、番号で戻せるようにする。取り消せない操作（データの削除・本番への反映・外部への送信）と、流れが変わる大きな作り直しはせず「判断がほしいもの」に回す。

## 7. 取り込み

マージコミットを作らず直線の履歴で取り込む（rebase / cherry-pick）。取り込むたびに確認を回し、最後に全部を通す。1回目に落ちて2回目で通ったテストは記録に書いて原因を直す。main の持ち主は ice-north で、変更はフォーク（ishidafuu）のブランチに push して PR にする（main へ直接 push しない）。

## 8. リファクタ

動きを変えない整理だけ（重複の統合・使われないコード・古いコメント・同じ取り決めの二重記述を1か所に）。テストの期待値は変えない。

## 9. 画面

主な作業をブラウザで最後までたどり、画面の例外・赤いエラー表示・押しても何も起きない物・余計なスクロールを確かめる。

## 10. 記録

`docs/audit/YYYY-MM-DD.md` に次を書いてコミットする: 範囲（開始..終わりのコミット）／確認の結果／エラーログの集計／直したもの／整理したもの／おすすめで実装したもの（Q番号・問・案・コミット）／判断がほしいもの（案とおすすめ）／気づいたが直していないもの。

## 11. 報告

短く。直した件数と重いもの数件、Q の数と「違うものは番号で」の一言、判断がほしいものの数、記録へのリンク。
